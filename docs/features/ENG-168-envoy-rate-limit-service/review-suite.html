RS-012 · HIGH · Deferred (proving test skipped)

hits_addend above MaxInt64 is reinterpreted as a negative hit and the call reports OK

Found byreview-tests reachability probe (Phase 5), refuting an 'unreachable clamp' claim
Stagereview-tests
Locationenvoy/rls.go ShouldRateLimit, hits computation `hits = int64(d.HitsAddend.Value)`; algorithms.go tokenBucketNewItem `Remaining: r.Limit - r.Hits`
Proving testTestHitsAddendAboveMaxInt64FailsTheCall (skipped) — envoy/envoy_test.go:1136
InvariantBlueprint principle 4 'Fail loud, never fail open silently'; CON-1 never report OK for an unevaluated descriptor

Summary — A descriptor whose hits_addend is 2^63 or larger is admitted with OK instead of failing the call.

Explainer

Envoy's RateLimitDescriptor.hits_addend is a google.protobuf.UInt64Value. The adapter converts it to gubernator's int64 hit count with an unchecked cast:

hits := int64(1)
if d.HitsAddend != nil {
    hits = int64(d.HitsAddend.Value)   // 1<<63 becomes math.MinInt64
} else if r.HitsAddend != 0 {
    hits = int64(r.HitsAddend)
}

For any value ≥ 2^63 the cast produces a large negative number. Gubernator treats negative hits as credit (that is documented behaviour for is_negative_hits), and in tokenBucketNewItem the expression Limit - Hits overflows to a negative Remaining. The status comes back UNDER_LIMIT, the adapter clamps the negative remaining to 0 and answers Envoy with OK.

Failure path: ShouldRateLimit{descriptor.hits_addend = 1<<63, limit 10/MINUTE} → hits = MinInt64 → bucket created with Remaining wrapped negative → status OK, limit_remaining 0 → Envoy forwards the request. Correct behaviour under the blueprint is a gRPC error (InvalidArgument) so failure_mode_deny decides. Blast radius: any caller that can set hits_addend — route config or the envoy.ratelimit.hits_addend filter-state key set by an upstream filter.

Evidence

--- FAIL: TestHitsAddendAboveMaxInt64FailsTheCall (0.00s)
    Error: An error is expected but got nil.

Repro (remove the t.Skip first): go test -run '^TestHitsAddendAboveMaxInt64FailsTheCall$' ./envoy/

Why it wasn't auto-fixed

review-tests never edits the implementation, and the finding surfaced after the logic-mutating stage had closed. Suite default: proving test left red and skipped in place.

Suggested fix

// envoy/rls.go, before the cast
if d.HitsAddend != nil && d.HitsAddend.Value > math.MaxInt64 {
    return nil, status.Errorf(codes.InvalidArgument,
        "domain %q descriptor %s: hits_addend %d exceeds %d",
        r.Domain, strings.TrimPrefix(name, r.Domain+"."), d.HitsAddend.Value, int64(math.MaxInt64))
}

Unambiguous; no consumer can depend on the current wraparound. Then remove the t.Skip at envoy/envoy_test.go:1137.

RS-011 · MEDIUM · Deferred (flaky; test left running)

AC-13 convergence is probabilistic when a peer cannot identify itself in its peer list

Found byreview-tests coverage run (Phase 5)
Stagereview-tests
Locationenvoy_policy.go otherPeers()/pull() (self excluded only via PeerInfo.IsOwner); daemon.go Daemon.SetPeers (IsOwner only when AdvertiseAddress == GRPCAddress); cluster/cluster.go StartWith (advertises localhost:port, listener reports 127.0.0.1:port)
TestTestRestartedPeerPullsPolicyWithinSyncInterval — envoy/envoy_test.go (not skipped: fails ~1 in 4 runs, passes otherwise)

Summary — A restarted peer's bootstrap and anti-entropy pulls choose a random peer including, in the test harness, itself, so the documented 'within one sync interval' bound only holds probabilistically there.

Explainer

Bootstrap and anti-entropy pull the policy set from one random peer taken from GetPeerList() minus entries flagged IsOwner. Daemon.SetPeers flags a peer as owner only when the string AdvertiseAddress equals the peer's GRPCAddress. The cluster helper advertises localhost:2116 while the listener reports 127.0.0.1:2116, so in tests no daemon is ever its own owner and the random pull can hit itself (returning its own empty set). With three peers that is a 1/3 miss per pull; three misses inside the test's 3-interval window ≈ 4%, and it was observed in 2 of ~10 package runs during this suite (once also surfacing as a transient 'client connection is closing' in the following test).

Production daemons resolve the advertise host through SetupDaemonConfig, so IsOwner is normally set — but any deployment where the advertised string differs from the peer-list string (hostname vs IP) reproduces the weakness: the peer wastes pulls on itself and converges later than the interval the docs promise.

Evidence

--- FAIL: TestRestartedPeerPullsPolicyWithinSyncInterval (3.01s)
    envoy_test.go:682: Condition never satisfied
    envoy_test.go:683: rpc error: code = Canceled desc = grpc: the client connection is closing

Repro (probabilistic): go test -count=20 -run '^TestRestartedPeerPullsPolicyWithinSyncInterval$' ./envoy/

Why it wasn't auto-fixed

The blueprint's Propagation section specifies 'one random peer'; widening that (try peers in random order until one answers) is a design change, and the harness fix (advertise the resolved listener address) touches cluster.StartWith, which every existing functional test relies on. Both are the user's call.

Suggested fix

Two independent improvements: (1) in otherPeers() also exclude a peer whose GRPCAddress equals the manager's origin (advertise address), and (2) make cluster.StartWith set AdvertiseAddress to the resolved listener address so IsOwner is set in tests. Optionally (3) have pull() iterate peers in random order until one returns a non-empty set, each bounded by GlobalTimeout, and update the Propagation section accordingly.
